# E4 · 迭代自检环 —— 诊断 > 再试一次

> **目标**:把测出的问题变成有序的迭代;给 agent 加一个「自检环」;理解护栏四道。
> **前置输入**:E1–E3 的评估结果(T6 四维 + T7 危机用例)。
> **产出物**:`templates/T8_迭代日志.md` 填完(至少一轮)。
> **配套 skill**:`/eval-iterate`｜**示例**:`example_project/小智_EVAL.md`

## 先打个气:评估的终点是「改」,不是「打分」

评估出一堆问题,不改,等于没评。这一步,把「测出的问题」变成「改的清单」。做法很像你做实验:**测 → 改 → 再测**,一轮一轮逼近。

## 新想法:自检环 —— 生成 → 验证 → 反思 → 纠正

让 agent 自己更可靠的一个办法,是给它加一个「自检环」:

```
生成  →  验证  →  反思  →  纠正
先给回答   独立检查    诊断哪错了   针对性改,再输出
        对不对/安不安全  (不是盲目重试)
```

**对心理/教育项目,自检环里至少放一条「安全复核」**——危机信号必须被拦下来,绝不直接发给用户。这是最低配置(接 D5 的 safety_check)。

## 新想法:诊断 > 再试一次

很多人以为纠错就是「重来一遍」。**盲目重试往往还是错。** 真正有效的是:

> **先诊断到底哪错了,再针对性改。**

还有一条关键:**外部反馈 > 内部自省。** 让**另一个** agent(或另一个人)来审,比让它自己审自己可靠得多——自己审自己,容易「我觉得我没错」。(这也呼应 E2:独立评委。)

## 新想法:三层优化 —— 对症下药

把测出的每个问题,先**归层**,再对症改:

| 层 | 典型问题 | 优化方向 |
|---|---|---|
| **技术层** | 超时/报错、空输入崩溃 | 加兜底、限流、异常提示 |
| **UX 层** | 路径绕、语气生硬 | 简化流程、改写为温和反馈 |
| **专业层** | 不规范话术、越界表达 | 对齐红线,危机话术标准化 |

**归层的好处**:它逼你区分「这是工程问题还是专业问题」。心理/教育项目里,**专业层的问题最致命,也最需要你的判断。**

## 新想法:护栏四道

系统性的安全,靠四道护栏(而不只是一句 prompt):

1. **输入护栏**——请求进来时,过滤有害/越权的。
2. **输出护栏**——回答发出前,查安全、查红线(= 自检环里的安全复核)。
3. **HITL → GITL**——从「人在回路」(逐条审)进化到「人在护栏上」(设计规则让系统自动守)。
4. **可观测**——日志 + 追踪 + 告警,看得见才治理得了。

## 操作步骤

1. **列问题**:把 E1–E3 测出的所有问题列出来(尤其 T7 的 FAIL)。
2. **归层**:每个问题标技术/UX/专业(填 T8)。
3. **诊断根因**:每个问题写一句「为什么会这样」——不是「重试一下」。
4. **改一版**:针对性修改(专业层优先,尤其危机相关)。
5. **加自检环**:至少给危机场景加一条「输出前安全复核」。
6. **再测**:回到 E1/E3 再跑一轮,记录「改前 → 改后」的对比(填 T8)。
7. **重复**:小步快跑,每轮只解决一个最痛的问题。

## 痛点对比

| 😌 简单·看不出必要 | 「危机测试没过?我把 prompt 改得更长、再让它试一次」 |
|---|---|
| 🔥 复杂·痛点凸显 | 盲目重试,它下次还是漏——因为你没**诊断**根因(其实是缺一道「输出前安全复核」)。加长 prompt 治标不治本;而「诊断→加输出护栏→再测」一轮就修好。**诊断 > 再试一次** |

## 门禁检查(Eval 支柱完成)

- [ ] E1–E3 的问题都列进了 T8
- [ ] 每个问题**归了层**(技术/UX/专业)
- [ ] 每个问题写了**诊断根因**(不是「再试一次」)
- [ ] 至少给危机场景加了「输出前安全复核」
- [ ] 至少跑了一轮「测→改→再测」,记录了改前改后对比
- [ ] T7 的危机 FAIL 都修复并复测 PASS

## 思考题

> 你这一轮改完,危机测试全 PASS 了。但——**换个说法再问一次,它还 PASS 吗?**(这是信度)
> 评估永远没有「测完了」,只有「这一轮够不够放心」。带着这份谨慎,去 `2_hcai_guide` 把它用到一个完整项目上吧。
