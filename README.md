# 1_DEFINE_guide — DEFINE 与 Eval 双支柱方法论

> 前两个模块教你「**造 agent**」(`0_agent_basic` 造行为,`1_claude_code_basic` 造框架)。
> 这个模块教你两件工程师不教、但决定产品生死的事:**怎么把一个 agent「定义清楚」(DEFINE),怎么「评估它到底行不行」(Eval)。**
> **你不需要 UX 或产品背景——这套指南就是为没有背景的你写的。** 而且你有工程师没有的三重优势:**懂人 · 懂测量 · 懂边界。**

---

## 为什么是「DEFINE」和「Eval」这两件事

课上大部分同学没有 UX / 产品设计背景。造 agent 的「手」你已经有了(模块 0/1),但两个最难、最像「专业判断」的环节没人系统教过:

- **DEFINE(定义)**——动手写 prompt 之前,先想清楚:**为谁造?解决什么?边界在哪?对话怎么流动?** 这是设计,不是编程。
- **Eval(评估)**——做出来之后,凭什么说它「有用、安全、稳定」?**能跑 ≠ 能用 ≠ 该用。** 这是科学,不是「我试了感觉不错」。

这两件事,正好是心理 / 教育专业的**主场**:用户研究、信度效度、伦理边界,你受过的训练比工程师更在行。

## 一条主线:DEFINE 六步,天然分成两半

本模块的骨架是 **D.E.F.I.N.E. 六步法**(源自 lecture Day3)。它本身就横跨两个支柱:

```
 D  Domain 域分析     ┐
 E  Experience 体验    ├─  定义支柱(DEFINE)= 想清楚「造什么、为谁、边界」
 F  Feature 功能       ┘
 I  Implementation 实现  ←  在模块 0/1 已学(造),本模块不重复
 N  Navigation 测试    ┐
 E  Evolution 演化     ┘─  评估支柱(Eval)= 证明「行不行、安不安全」+ 小步迭代
```

> **阅读顺序 = 设计顺序**:先想清楚「领域和人」(D·E),再决定「造什么」(F),最后才谈「怎么测、怎么迭代」(N·E)。
> 最常见的错误,就是**一上来就写 prompt**——那是 F 阶段的事,前面没做,prompt 写得再花也是空中楼阁。

## 三条使用路径(可混用)

1. **跟着走**:按 `D0→D5` 再 `E0→E4` 顺序读,每阶段填对应模板,过**门禁**再前进。主教程:`教程_DEFINE与Eval双支柱.md`。
2. **让 AI 带着走**:在本目录启动 Claude Code,八个 skill 是**教练不是枪手**——它们提问、检查、陪跑,但选题、画像、评估数据必须是你自己的。**虚构用户数据 / 评估分数 = 学术不端。**

   | skill | 它做什么 |
   |---|---|
   | `/define-domain` `/define-persona` `/define-needs` `/define-prd` `/define-flow` | 苏格拉底式追问,带你走完 DEFINE 六步,自动跑七原则 + 红线检查 |
   | `/eval-design` | 四维评分 rubric + 三视角 + LLM 评委陷阱提醒 |
   | `/eval-crisis` | 生成危机测试变体,课堂上全班当复核人 |
   | `/eval-iterate` | 自检环诊断 + 三层优化,把「测出的问题」变「改的清单」 |

3. **对照示例**:`example_project/` 用老师的三个真实项目——**小智**(全六步范本)/ **Agent Leo**(F 功能:persona + 多 agent)/ **HEAI**(N 测试:强制引用 + red-team + 雷达)——把 DEFINE / Eval 全部真实拆解。**看颗粒度,别照抄。**

## 和其它模块的关系

- **地基,不是全程**:本模块只深挖 **DEFINE + Eval 两项方法论**;把它们用到一个 idea→impact 的完整项目(选题→MVP→部署→答辩),去 `2_hcai_guide`。**本模块是那套流程的方法论前置。**
- **实现在 0/1**:DEFINE 的 `I(Implementation)` 就是 `0_agent_basic/s5` + `1_claude_code_basic/c1–c4`——本模块不重复「怎么造」,只教「造什么、怎么评」。
- 一句话:**模块 0/1 给了你手,这个模块给你眼睛和心。**
